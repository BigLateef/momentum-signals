# Momentum Signals — Lateef's Alpha Terminal

Invite-only momentum trading signal dashboard. Next.js 14 (App Router) + Neon Postgres + Drizzle ORM, deployed on Vercel. Signals can be posted manually by an admin, pushed in by an external bot, or auto-generated by the built-in DexScreener scanner.

## Architecture

```
Landing (/) ──code──▶ Login/Signup (/auth/login) ──session──▶ Dashboard (/auth/dashboard)
                                                                      │
Admin (/admin) ◀── admin-only session ────────────────────────────────┘

Signal sources:
  1. Admin Panel → Post Signal tab        → POST /api/signals
  2. External bot/scanner (yours)         → POST /api/triggers/signal   (Bearer CRON_API_KEY)
  3. Built-in DexScreener scanner (cron)  → POST /api/cron/scan         (Bearer CRON_API_KEY)
  4. Price refresher (cron)               → POST /api/cron/update-prices (Bearer CRON_API_KEY)

All signal sources write to the same `signals` table in Neon; the dashboard
doesn't know or care which source posted a given row.
```

## Features

- Invite-code gated landing page → signup/login (single-use codes, admin-generated only)
- Signal feed with chain/type filters, watchlist (★), and live polling (20s)
- Live P&L badge per signal (current price vs. entry, from the price cron)
- Admin panel: generate/revoke invite codes, manage signals, post new signals, manage users, manage tracked KOL wallets, view performance stats, view audit log
- **Automated momentum scanner**: pulls DexScreener's boosted/trending tokens across 8 chains, scores them, auto-posts qualifying BUY/ALERT signals
- **Automated price refresher**: keeps `current_price` live on all active signals, auto-deactivates any that blow through stop loss
- **Mistral AI-enriched reasons**: auto-posted signals get a readable one-sentence narrative instead of just raw numbers (optional, falls back gracefully)
- **KOL wallet tracking**: flags when a token's top holders include an admin-tracked KOL wallet (optional per chain, needs explorer API keys)
- **Discord alerts**: HIGH-confidence signals ping a Discord webhook automatically (optional)
- **Audit log**: every admin/system action (invite generated/revoked, signal posted/deactivated, session revoked, KOL wallet added/removed) is recorded with actor + timestamp
- **Session revocation**: admin can force-logout any user instantly, invalidating their session on every device
- **Performance stats**: win rate, average return, best/worst performer, broken down by chain — both realized (closed) and unrealized (open) signals
- Rate limiting (Upstash Redis) on auth + invite validation routes
- Public `/api/triggers/signal` endpoint for your own external scanners/bots, secured with a bearer API key

## 9. Wire up the automated scanner + price feed (required — nothing runs without this)

The scanner and price refresher are just passive API routes — nothing calls them on a schedule until you set that up. On Vercel's Hobby (free) tier, **Vercel Cron only runs once per day**, which is too infrequent for a momentum scanner, so use [cron-job.org](https://cron-job.org) instead — it's free with no meaningful rate limits for this use case (you're making 2 requests every few minutes, well under their free-tier ceiling).

### Step-by-step: cron-job.org setup

1. **Create a free account** at [cron-job.org](https://console.cron-job.org/signup).
2. Once logged in, click **CREATE CRONJOB** (top right).

**Job 1 — Scanner (finds new momentum plays)**
3. **Title:** `Momentum Signals — Scanner`
4. **Address (URL):** `https://your-domain.vercel.app/api/cron/scan` (use your actual Vercel domain)
5. **Schedule:** click "Every X minutes" → set to every **20 minutes** (or your preference; DexScreener's boosted-token list doesn't refresh faster than that anyway)
6. Expand **Advanced** (or "Request method / Headers" depending on their current UI):
   - **Request method:** `POST`
   - **Headers:** add a header —
     - Key: `Authorization`
     - Value: `Bearer YOUR_CRON_API_KEY` (paste the exact value you set for `CRON_API_KEY` in Vercel, with `Bearer ` in front and a space after it)
7. **Save.**

**Job 2 — Price refresher (keeps current_price and P&L live)**
8. Click **CREATE CRONJOB** again.
9. **Title:** `Momentum Signals — Price Refresh`
10. **Address (URL):** `https://your-domain.vercel.app/api/cron/update-prices`
11. **Schedule:** every **10 minutes**
12. **Request method:** `POST`, same `Authorization: Bearer YOUR_CRON_API_KEY` header as above
13. **Save.**

### Verifying it's actually running

- On cron-job.org, click into either job → **Execution history**. Each run shows a status code and response time. `200` = success; anything else means check the response body for the error.
- Click **"Execute now"** on either job to trigger it manually and confirm it works before waiting for the schedule.
- A successful scan response looks like `{ "scanned": 12, "posted": 1, "postedDetails": [...], "skipped": 11 }` — `posted: 0` most runs is normal, it just means nothing cleared the momentum threshold that cycle.
- If you get `{ "error": "Unauthorized" }`, your `Authorization` header value doesn't exactly match `Bearer <CRON_API_KEY>` — check for extra spaces, missing "Bearer ", or a stale/regenerated key.
- Check your own Vercel deployment logs (Vercel dashboard → your project → Logs) to see the actual function execution and confirm requests are arriving.

### Why there's no vercel.json in this repo

An earlier version of this project included a `vercel.json` with Vercel Cron entries running every 10–20 minutes. **This breaks deployment on Hobby** — Vercel rejects any cron schedule more frequent than once/day at deploy time, failing the entire build (this is what caused the red ✕ on GitHub if you saw one). It's been removed. cron-job.org is your scheduler; you don't need Vercel Cron at all on Hobby.

If you ever upgrade to Vercel Pro and want to switch to (or add) Vercel Cron instead of/alongside cron-job.org, create `vercel.json` in the project root with:

```json
{
  "crons": [
    { "path": "/api/cron/scan", "schedule": "*/20 * * * *" },
    { "path": "/api/cron/update-prices", "schedule": "*/10 * * * *" }
  ]
}
```

Then set a `CRON_SECRET` env var in Vercel to the same value as `CRON_API_KEY` — Vercel Cron sends `GET` requests with that as an auto-attached bearer token, and both routes already accept `GET` for this reason.

## How the momentum scanner works

Every scan run (`/api/cron/scan`):

1. Fetches DexScreener's `token-boosts/latest/v1` — tokens currently being promoted/trending across Solana, Base, BNB Chain, and Ethereum.
2. For each token, pulls its highest-liquidity trading pair (price, volume, liquidity, txn counts).
3. **Filters out anything with < $5,000 liquidity or < $10,000 24h volume** — too thin to trust the price action.
4. Scores the remaining tokens 1–10 (`src/lib/momentum.ts`) from three weighted components:
   - **Momentum** (up to 5 pts): 1h price change weighted more than 6h change
   - **Volume/liquidity ratio** (up to 3 pts): healthy turnover relative to pool depth
   - **Buy/sell pressure** (up to 2 pts): skew toward buys in the last hour
5. Assigns confidence (LOW/MEDIUM/HIGH) from raw liquidity + volume thresholds.
6. Posts a `BUY` signal if score ≥ 7 with positive 1h momentum, an `ALERT` if score ≥ 5, otherwise skips.
7. **Dedupes**: won't re-post the same contract address + chain if it already has an active signal from the last 6 hours.
8. TP1/TP2/stop-loss are set at a flat +15% / +30% / −15% from entry as a starting heuristic — **tune these in `src/lib/momentum.ts`** to match your own risk tolerance; they are not a strategy recommendation.

This is a heuristic, not a trading strategy — it surfaces candidates worth a manual look, the same way your other bots' scanners do. Treat auto-posted signals as raw material, not gospel.

## Optional integrations

All of these are opt-in via env vars — the app works fully without any of them, just with fewer bells and whistles.

### Discord alerts

Set `DISCORD_WEBHOOK_URL` (create one in Discord: Server Settings → Integrations → Webhooks). Any signal with `confidence: "HIGH"` — manually posted, externally triggered, or scanner-posted — pings that webhook with an embed. No key = silently skipped.

### Mistral AI-enriched reasons

Set `MISTRAL_API_KEY` ([console.mistral.ai](https://console.mistral.ai), free tier available). When set, every scanner-posted signal gets its templated `reason` rewritten into a short, readable sentence by `mistral-small-latest`. **This is cosmetic only** — it never touches the score, confidence, or signal type, which stay fully deterministic from `src/lib/momentum.ts`. If the Mistral call fails or times out (4s budget), the original templated reason is used instead — enrichment never blocks a signal from posting.

### KOL wallet tracking — honest limitations

Add wallets in Admin → KOL Wallets. When the scanner posts a signal, it checks that token's top holders (via the chain's block explorer API) against your tracked list and shows a 🐋 badge if there's a match.

**Be aware of what this can and can't actually do:**
- Needs one API key per chain you want checked (`ETHERSCAN_API_KEY`, `BSCSCAN_API_KEY`, `BASESCAN_API_KEY` for EVM chains, `SOLSCAN_API_KEY` for Solana). Unlike DexScreener, none of this is free-and-keyless — every one of these needs a signup, though all have workable free tiers.
- "Top holders" endpoints typically only return the top 20–100 addresses. A KOL holding a smaller amount outside that range won't be caught.
- Free-tier explorer APIs are rate-limited (Etherscan-family is ~5 req/s on a free key). Fine for checking the handful of tokens that clear the momentum threshold each scan; not built for scanning hundreds of tokens.
- No coverage for Arbitrum, Polygon, Avalanche, or Optimism yet — `EXPLORER_CONFIG` in `src/lib/kol.ts` only wires up Ethereum/BNB/Base. Add entries there (Arbiscan, Polygonscan, Snowtrace, Optimistic Etherscan all have the same API shape) if you want those covered too.
- Missing a chain's key doesn't error — that chain's checks are silently skipped, same pattern as everything else optional in this app.

### Session revocation

Admin → Users → "Force logout" immediately invalidates every session token issued to that user, on every device — not just cosmetic. This works by checking a `session_version` counter against the DB on every authenticated request (both in middleware and in `getSession()`), so it costs one extra DB read per request but makes revocation actually effective against stateless JWTs.

### Performance stats

Admin → Performance shows win rate, average return, and best/worst performer, split into **closed** (deactivated — return is realized/frozen) and **open** (still active — return is unrealized, based on the last price-refresh cron run) signals, plus a breakdown by chain. This is purely computed from `entry_price`/`current_price` already on the `signals` table — no extra data source needed.

### Audit log

Admin → Audit Log records every admin and system action: invite codes generated/revoked, signals posted/deactivated/reactivated, sessions force-revoked, KOL wallets added/removed, and scanner runs that posted signals. Actor is either an admin's email or a system label (`system:scanner`, `system:external-trigger`).

## Troubleshooting

**Admin badge not showing after promoting yourself to admin:**
The role is embedded in the session JWT at login time — a DB update alone doesn't refresh an already-issued cookie. Log out (not just close the tab), then log back in. If it still doesn't show, confirm the DB actually updated: `SELECT email, role FROM profiles WHERE email = '...'`.

**Vercel build fails with a `useSearchParams()` / Suspense error:**
Already fixed in this codebase — `LoginForm` (which calls `useSearchParams`) is wrapped in `<Suspense>` inside `src/app/auth/login/page.tsx`. If you see this again after editing that file, re-wrap whatever new component calls `useSearchParams`.

**Existing users get asked for a new invite code when trying to log back in:**
Already fixed — the landing page has an "Already have an account? Log in" link that goes straight to `/auth/login` without requiring a (now-consumed, single-use) invite code.

**Scanner isn't posting anything:**
Check cron-job.org's execution log for the response body — `{ scanned: N, posted: 0, skipped: N }` means DexScreener returned boosted tokens but none cleared the liquidity/volume/momentum thresholds, which is normal on quiet days. `scanned: 0` means the boosted-tokens fetch itself came back empty or failed.

## Notes

- Invite codes are strictly single-use: one code, one signup, then it's marked used and can't be reused, even by the same person. Only an admin can generate codes, from the Admin panel.
- Invite codes exclude ambiguous characters (`I`, `O`, `0`, `1`).
- Sessions are stateless JWTs (7-day expiry) in an HTTP-only cookie — role changes require re-login.
- Middleware (`src/middleware.ts`) protects `/auth/dashboard/*` and `/admin/*`.
- The scanner and price feed cover Solana, Base, BNB Chain, Ethereum, Arbitrum, Polygon, Avalanche, and Optimism — extend `CHAIN_MAP` in `src/lib/dexscreener.ts` for more.
- KOL wallet checking currently only has explorer API wiring for Ethereum, BNB, Base, and Solana (see the KOL section above for how to add more).
- Not built in this pass, worth adding later if useful: signal edit UI (currently deactivate-only), configurable scanner thresholds from the admin panel instead of code, session revocation via a "current sessions" list per user (currently an all-sessions bump).

## Upgrade: anti-rug safety, automated trading, and the unified scheduler

This section documents the three additions layered on top of the existing app. None of it replaces auth, the dashboard, the Drizzle schema's existing tables, the scanner, price-refresh, signal lifecycle, or admin workflow — everything here is additive.

### 1. Database provider — Neon or Supabase, auto-detected

No code changes needed to switch providers — `src/db/raw-client.ts`'s `detectDriver()` reads the hostname out of `DATABASE_URL` and picks the right driver automatically:

| `DATABASE_URL` host | Driver used | Why |
| --- | --- | --- |
| `*.neon.tech` | `drizzle-orm/neon-http` (fetch-based, no persistent connection) | What this app was originally built around — ideal for serverless, unchanged from before this upgrade |
| Anything else (Supabase, Railway, RDS, self-hosted, ...) | `postgres.js` over a real TCP connection | The safe general-purpose choice for any standard Postgres |

Override the guess with `DB_DRIVER=neon` or `DB_DRIVER=postgres` if you're ever on a hostname the auto-detection gets wrong.

**If you're using Supabase:** Project Settings → Database → Connection string → URI, and pick **Transaction pooler** (port 6543) — the screen where you choose this literally says "Direct connection", "Transaction pooler", "Session pooler". Do **not** pick Direct connection for this app: it isn't pooled, and a serverless function opening a fresh connection on every invocation will exhaust Postgres's connection limit under any real traffic. Session pooler works too if you're on an IPv4-only network and can't reach the transaction pooler, but transaction pooler is the better default.

**One real architectural constraint this creates, and how it's handled:** `src/middleware.ts` (the session-revocation check that runs on every protected page load) executes on Next.js's **Edge runtime**, which only supports `fetch`-based I/O — it cannot open the raw TCP socket `postgres.js` needs. On Neon, middleware queries directly over HTTP exactly as it did before this upgrade (zero behavior change). On Supabase/Postgres, middleware instead calls a small Node.js-runtime API route (`/api/internal/session-check`) that does the same check using `postgres.js`, authenticated by re-verifying the caller's own already-valid session JWT rather than a separate shared secret. Functionally identical outcome, different mechanism per driver, because Edge Runtime genuinely can't do otherwise.

Every raw-SQL script (`src/db/migrate.ts`, `src/db/run-migration.ts`, `src/db/seed-admin.ts`) goes through the same `createStatementRunner()` in `src/db/raw-client.ts`, so they all follow the same auto-detection and work against either provider identically.

### 2. Run the migration

**In Termux, no web SQL editor and no `psql` install required** (uses the same driver-detection layer described above — works against Neon or Supabase):

```
npm install
export DATABASE_URL="postgresql://...your Neon or Supabase connection string..."
npx tsx src/db/run-migration.ts migrations/003_safety_and_trading.sql
```

or, if you already ran `npm install`, the shorter form:

```
npm run db:migrate:file migrations/003_safety_and_trading.sql
```

Prints each statement as it runs and stops immediately on any real error (the file is additive — see below — so a failure partway through is safe to fix and re-run; every `CREATE TABLE`/`ADD COLUMN` uses `IF NOT EXISTS`).

**Alternative, if you'd rather use a native `psql` client:** `pkg install postgresql -y` in Termux, then `psql "$DATABASE_URL" -f migrations/003_safety_and_trading.sql`. Either approach applies the identical SQL — the Node-based route above just avoids the extra Termux package install.

The migration is **raw hand-written SQL, not Drizzle-managed** — this project has never run `drizzle-kit generate` (there's no `/drizzle` output folder or migration journal), matching the existing `002_features.sql` convention. `drizzle.config.ts` exists only so `drizzle-kit` can introspect `src/db/schema.ts` for type-checking; it isn't used to generate or apply these numbered migration files.

It's fully additive: every new table uses `CREATE TABLE IF NOT EXISTS`, every new column uses `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, and nothing is dropped or recreated. Commented-out rollback SQL is included at the bottom of the migration file itself.

### 3. Anti-rug / token safety

- **Providers, no keys needed:** [RugCheck.xyz](https://rugcheck.xyz) for Solana, [GoPlus Security](https://gopluslabs.io) for the other seven EVM chains this app already scans.
- **Every check that can't be answered from real data is marked `UNKNOWN`** with "Safety data unavailable" — nothing is guessed. In particular: LP lock **expiry** timestamps, deploy-and-dump price history, and wallet-clustering/linked-wallet graphs aren't exposed by either free provider, so those three checks are always `UNKNOWN` unless you wire in a paid provider that supports them.
- **Deployer history** is built from this platform's own accumulated `token_safety_reports` rows (grouped by deployer address) rather than a third-party API — it only has data once you've analyzed more than one token from the same deployer.
- Verdicts, worst to best: `BLOCKED`, `CRITICAL`, `VERY_HIGH_RISK`, `HIGH_RISK`, `CAUTION`, `LOW_RISK`, plus `INSUFFICIENT_DATA` when most checks came back unknown. `BLOCKED` / `CRITICAL` / `INSUFFICIENT_DATA` block automatic publication and trading outright; `VERY_HIGH_RISK` requires an admin override (stored with admin ID, reason, timestamp — see the Signals tab).
- **Important architectural note:** the scanner posts a signal, then the safety stage analyzes it and deactivates it if blocked — safety analysis can't run *before* insertion without restructuring the scanner's dedupe logic, so "blocks automatic publication" means "the signal exists in the DB for a few seconds before being deactivated," not "is never inserted." It never appears active/visible on the dashboard by default (`isActive=false`), which is the practical equivalent, but it's worth knowing if you're auditing the DB directly.

### 4. Automated trading

- **Burner wallet:** set `AUTO_TRADE_WALLET_PRIVATE_KEY` (base58 for Solana, hex for BNB). This key is loaded only in `src/lib/trading/wallet.ts`, a server-only module — it is never returned by any API response, logged, or written to the DB.
- **Live trading requires setting BOTH `AUTO_TRADE_ENABLED=true` AND `AUTO_TRADE_DRY_RUN=false` explicitly.** Every other combination either does nothing or only logs decisions. Do not enable both during initial deployment — verify dry-run output first.
- **Execution:** Solana trades route through Jupiter's public swap API; BNB trades route through PancakeSwap V2 directly via `ethers`. Both are real, working integrations, not stubs — but neither has been run against mainnet by Claude (no network access in this sandbox). Test with `AUTO_TRADE_DRY_RUN=true` and small `AUTO_TRADE_AMOUNT_SOL`/`AUTO_TRADE_AMOUNT_USDC` first.
- **Emergency kill switch:** Admin panel → Auto-Trade tab. This is a DB-backed toggle (`system_settings` table) an admin can flip instantly without a redeploy — it's checked in *addition to* `AUTO_TRADE_ENABLED`, so either one blocks trading.
- **A trade is never blindly retried.** If a confirmation check times out or errors, the execution row stays `SUBMITTED` rather than being reported as failed or retried — check it manually or re-run `/api/triggers/execute-trade` for a fresh signal instead.
- **Daily loss tracking is a heuristic**, not a full cost-basis ledger: it estimates realized loss from confirmed SELL executions' quoted-vs-executed price delta. Treat `AUTO_TRADE_MAX_DAILY_LOSS_USD` as a circuit breaker, not an accounting figure.

### 5. Cron consolidation

**`/api/cron/monitoring-scheduler` is the only recommended production scheduler.** Set `MONITORING_SCHEDULER_ENABLED=true` and point your one cron-job.org schedule at this route, firing every `MONITORING_SCHEDULER_INTERVAL_MINUTES` minutes (default 5). The route also self-enforces that interval server-side — if it's triggered again before that many minutes have passed since the last run started (e.g. a second cron-job.org schedule pointed here by accident, or a manual + automatic run overlapping), it skips immediately without attempting the lock, so overly-frequent triggers can't pile up wasted Neon reads even before the lease lock would catch a truly concurrent call. It runs everything — discovery, safety, signal creation, auto-trade, price refresh, TP/SL/invalidation, monitoring, performance, and one consolidated summary alert — under a single lock, and once enabled it makes `/api/cron/scan`, `/api/cron/update-prices`, and `/api/cron/market-cycle` all no-op automatically (they return `{ skipped: true }` without touching the database), so there is no supported production configuration where more than one of these routes is doing real work at the same time.

`/api/cron/market-cycle` exists only as a manual/rollback path (run it with `?force=true`, or point cron-job.org at it temporarily instead of the scheduler if you need to disable the newer monitoring/performance stages without losing the core scan+safety+trade+price pipeline). `/api/cron/scan` and `/api/cron/update-prices` exist only for emergency rollback to the pre-upgrade two-job setup. None of the three legacy/standalone routes should be your primary production cron target going forward.

**Vercel Hobby caveat:** the monitoring-scheduler runs up to 12 stages sequentially. Hobby's function timeout is a fixed 10 seconds regardless of `maxDuration` in code — on a busy scan (many boosted tokens, several safety re-checks) this can get killed mid-run. That's safe (the lease-based lock expires on its own and the next scheduled hit picks up cleanly), but if you're seeing partial health reports, either reduce the per-run workload (fewer stale-signal re-checks — edit `MAX_RECHECKS_PER_RUN` in `src/lib/cycle/safety.ts`) or upgrade to Vercel Pro, where `maxDuration` is actually honored.

**Why a DB-row lock instead of `pg_advisory_lock`:** two reasons, one per driver. On Neon's HTTP driver (`drizzle-orm/neon-http`), each query is its own HTTP request with no persistent session — a session-scoped advisory lock can't span multiple requests at all. On a real TCP connection (Supabase or any other Postgres), this app is meant to run behind a transaction-mode pooler for serverless compatibility (see the Supabase setup section below) — and transaction-mode pooling can hand a different physical connection to each statement, which breaks session-scoped advisory locks just as thoroughly, just for a different reason. `src/lib/cron-lock.ts` implements a lease-based row lock instead (claim by conditional `INSERT ... ON CONFLICT ... WHERE expired`), which works identically regardless of driver or pooling mode. This is verified logically correct (tested the exact SQL pattern's atomicity), not just assumed — see the verification report for details.

### 8. Preserving live trading disabled by default

Every default in this upgrade is chosen so that deploying it with no new env vars set changes **nothing** about current behavior: `AUTO_TRADE_ENABLED` defaults false, `AUTO_TRADE_DRY_RUN` defaults true, `MONITORING_SCHEDULER_ENABLED` defaults false (legacy cron routes keep running exactly as before), and the kill-switch migration seeds `auto_trade_kill_switch = 'false'` (engaged is opt-in, but so is trading itself). You have to explicitly flip three separate things — `AUTO_TRADE_ENABLED`, `AUTO_TRADE_DRY_RUN=false`, and a funded `AUTO_TRADE_WALLET_PRIVATE_KEY` — before any transaction can broadcast.
